| | `quip-pipeline` / `quip-render` (Jobs) | **`quip-api` (Service)** |
|---|---|---|
| Память | 32 GiB | **8 GiB** |
| CPU | 8 | **2** |
| Диск под временные файлы | **32 GiB ephemeral-disk** + `TMPDIR` | **тома НЕТ → `/tmp` и `DATA_ROOT` = RAM** |

Редакторные эндпоинты синхронно, внутри HTTP-запроса, качали `source.mp4` **в оперативку** (ФС
Cloud Run = RAM), извлекали ~1500 JPG на 25 fps **туда же**, гоняли PySceneDetect + MediaPipe +
torch-ASD и кодировали mp4. Один такой запрос раздувал контейнер до 8233 MiB → Cloud Run убивал
контейнер → **все запросы внутри получали 503**. Кто не попал под OOM — упирался в 300 с → 504.

## Четыре независимых бага (а не один)

### 1. `/export/clean.mp4` — отказ ПО ПОСТРОЕНИЮ
Он **всегда** качал source, **всегда** пересчитывал CV, **всегда** кодировал и отдавал файл
**через контейнер** (`FileResponse`). Composite-fast-path его физически не спасал — тот закрыт
условием `if with_subtitles:` (`tasks.py:243`), а clean зовёт рендер с `with_subtitles=False`.

**Самое важное:** этот отказ **уже был описан в нашем же коде** (`fast_export.py:76-80`):
> «эндпоинт скачивает весь source (~10GB) в RAM-backed FS Cloud Run → OOM/503, а рендер идёт
> >300s > request timeout… путь ре-рендера — ГАРАНТИРОВАННЫЙ отказ»

10 июля мы починили ровно это — **но только для `captioned.mp4`** (302-редирект на CDN).
`clean.mp4` остался в состоянии, которое сами же назвали гарантированным отказом.
→ Фикс: 302 на запечённый `clips/<id>.mp4` (объект неизменяем — `upload_clip` его не перетирает),
под СТРОГИМ гейтом `should_serve_baked_clean`.

### 2. `/reframe` — «редкий фолбэк», ставший основным путём

> **⚠️ ГИПОТЕЗА БЫЛА ОПРОВЕРГНУТА ДАННЫМИ — читай до конца.** Сначала я решил, что виноват пустой
> кэш после `set reframe_regions = null`. Версия объясняла ВСЕ улики, была внутренне
> непротиворечива и **частично верна** (28 из 53 джоб действительно сидят с пустым кэшем — это
> заряженная мина). Но SQL по пострадавшим показал `regions_baked = true` у **всех** их клипов.
> Настоящая причина — ниже.

Fast-path требует ВСЕХ трёх условий: `lock_per_shot` И `persisted` И `intervals_match_default`.
Промах → полный CV. Причины промахов:
- **режим FOLLOW (`lock_per_shot = False`) — ЭТО И ЕСТЬ УБИЙЦА** (см. ниже);
- `reframe_regions = NULL` (наша же инструкция от 7 июля) — реальная мина, но не причина ЭТОГО;
- клип **тримили** (`len(intervals) != 1`).

#### ☠️ Настоящая причина: FOLLOW-режим не может использовать кэш В ПРИНЦИПЕ

Что общего у клипов, падавших в логах:

| Клип | `lock_per_shot` | `regions_baked` |
|---|---|---|
| `job_0c3e…/clip_29` (503 ×3) | **false** | true |
| `job_0c3e…/clip_12` (503 ×4) | **false** | true |
| `job_0c3e…/clip_02` (503 ×2) | **false** | true |
| `job_bc7c…/clip_06` (504 ×2) | **false** | true |
| `job_bc7c…/clip_09` (500) | **false** | true |

**Пять из пяти.** Регионы ЕСТЬ — но клип их не берёт. Наш собственный комментарий в `main.py`:

> «follow (`lock_per_shot=False`) **НЕ может брать запечённые регионы (они LOCKED)** → пересчёт ниже»

Запечённый план **всегда** locked. Значит follow-клип не может попасть в fast-path **никогда**, и
backfill для него тоже не срабатывает (он требует `lock_per_shot`). Итог:

> **Каждый юзер, переключивший клип в Follow, получает полный 3-минутный пересчёт CV на КАЖДОЕ
> открытие этого клипа. Навсегда. Независимо от кэша.**

Именно это и делал `mergen1show`: 5 клипов в Follow, открывал их снова и снова.

**Фикс:** follow-план кэшируется под ключом `{clip_id}#follow` в той же jsonb-колонке. Миграция НЕ
нужна: RPC `merge_reframe_regions` пишет `jsonb_build_object(p_clip_id, p_value)` → ключ = любая
строка, а `||`-merge не перетирает соседний ключ. Канонический LOCKED-ключ остался байт-в-байт.
Читают симметрично **и превью, и рендер** — асимметрия дала бы тихий разъезд превью и скачанного
файла.

**Ирония, ради которой этот файл и написан:** миграция `0013_reframe_regions.sql` была написана
ИМЕННО чтобы обезвредить эту бомбу. Цитата из её же комментария:
> «эти регионы НИГДЕ не персистились → `/reframe` пересчитывал тяжёлый CV на лету; на холодном
> контейнере он медленный/падает (**видели 500 на `/reframe`**)»

Она сработала. А потом инструкция «сбрось кэш регионов» **сняла предохранитель обратно** — и никто
не связал два факта, записанных в разных местах. Кэш-клир был технически необходим; недостающим
звеном было знание, что он ПЕРЕВОДИТ 100% трафика на путь, спроектированный как «изредка».

Добивает то, что **клип не всегда самолечится**: backfill требует `len(region_lists) == 1` и
`persisted is None`, а запрос, упавший по OOM, до backfill вообще не доходит → **клип навсегда
в петле отказа**. Отсюда одни и те же `clip_12` / `clip_29` / `clip_02` в логах.
→ Фикс: промах на дефолтном интервале → диспатч Cloud Run Job (32 GiB) → 202 + поллинг.
Изменённый интервал → CV остаётся в API, но за семафором и уже на диске, а не в RAM.

### 3. `httpcore.ConnectTimeout: SSL handshake timed out` → 500
Во всём воркере **не было ни одного переиспользуемого httpx-клиента**: все ~60 вызовов к Supabase
шли через `httpx.get(...)`, который на КАЖДЫЙ вызов делает полный TLS-handshake и закрывает
соединение. IDOR-гейт (`_require_owned_job`, ~35 эндпоинтов) даёт **4–5 вызовов на один запрос**.
При concurrency=80 на 2 ядрах, занятых CV → до **400 конкурентных рукопожатий**; бюджет
`connect=5s` (`supa.py:22`) не выдерживал. Ретраев не было нигде, глобального обработчика не было
→ **любой сетевой блип становился жёстким 500**.
→ Фикс: пул (`app/http_client.py`, keep-alive; замер 113 мс → 32 мс) + **method-aware** ретраи с
full-jitter backoff (connect-фаза — все методы: запрос заведомо не дошёл; потерянный ответ — только
идемпотентные, иначе можно списать деньги дважды) + backstop `httpx.TransportError → 503 + Retry-After`.

### 4. (Найден попутно) Молча неверное скачивание при склейке шотов
`edit_matches_baked` не проверял `suppressed_cuts`. А MERGE в `apply_cuts_to_regions` навязывает
второму шоту кадр ПЕРВОГО → пиксели меняются. Значит юзер, склеивший шоты, **молча скачивал baked
со старым кадрированием**, хотя превью показывало склеенное. WYSIWYG сломан, без единой ошибки —
прямое нарушение правила №8. `manual_cuts` (SPLIT) пиксель-нейтральны (обе половины наследуют
mode) → остаются разрешены. Асимметрия зафиксирована тестом.

### 5. (Фронт) Стампид × 3–4 и ФАЛЬШИВАЯ полоса шотов
`prefetchNeighbors` не дедуплицировал in-flight (запись в кэш появляется только когда зарезолвятся
все 4 запроса, а `/reframe` идёт 3 минуты → `has(clip)` всё это время false → каждый триггер
запускает ЕЩЁ ОДИН пересчёт). Плюс LRU размера 3 и полное отсутствие `AbortSignal`. Это и есть
**множитель аварии**: один клип = 3–4 параллельных пересчёта по гигабайту.
И при сбое `/reframe` фронт **молча рисовал ровные временны́е чанки** вместо реальных склеек — без
тоста, без ошибки. Пользователь думал, что видит AI-разметку шотов.

## Мина, обезвреженная попутно
`deploy/cloudrun/deploy.ps1:123` содержал `--cpu=1 --memory=4Gi`, тогда как прод стоял на 8Gi/2CPU
(поднято руками 10 июля). **Перезапуск скрипта молча откатил бы прод вдвое.**

## Уроки

0. **☠️ ПРОВЕРЯЙ ГИПОТЕЗУ ДАННЫМИ, А НЕ РАССУЖДЕНИЕМ.** Версия «виноват кэш-клир» объясняла ВСЕ
   улики — бимодальную латентность, OOM, петлю отказа — и была **частично верна**. Именно поэтому
   она была опасна. Если бы мы починили по ней, OOM бы ушёл, `mergen1show` продолжал бы ждать по
   3 минуты на каждый клип, а мы бы считали задачу закрытой. Спас **один SQL-запрос к боевой БД**.
   Красивая гипотеза, объясняющая все симптомы, — это ещё не диагноз.
1. **«Мы уже это чинили» ≠ «это починено».** Фикс `captioned.mp4` (302 на CDN) не был применён к
   `clean.mp4`, хотя болезнь одна. Чиня класс багов — **грепни весь класс**, а не один вход.
2. **Инструкция может снимать предохранитель.** `set reframe_regions = null` был необходим, но
   вернул систему в состояние, от которого её спасала миграция 0013. Если действие возвращает
   систему в прежде-сломанное состояние — это должно быть написано **рядом с инструкцией**.
3. **Стоимость запроса к БД в коде невидима.** `httpx.get()` выглядит дёшево, как обращение к
   словарю, но это TLS-рукопожатие. Умножь на IDOR-гейт и на concurrency — получишь аварию.
4. **Фолбэк, который врёт, хуже ошибки.** Фальшивая полоса шотов «работала» — и потому никто не
   заводил баг.
5. **Дефолты Cloud Run — это решение, даже если его никто не принимал.** concurrency=80 и
   timeout=300s никто не выставлял; они просто были.
