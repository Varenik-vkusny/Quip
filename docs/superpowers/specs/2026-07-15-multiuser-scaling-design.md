# Спек: масштабирование под многопользовательскую нагрузку (веб-тир + справедливость рендера)

> Дата: 2026-07-15 · Автор сессии: агент (оркестратор) · Статус: **DESIGN APPROVED, план не написан**
> Подход: **B — «Изоляция + справедливость»** (без переписывания архитектуры; цель — 5–10 юзеров разом).

## 1. Проблема (со слов основателя)

«Сайт еле-еле держит одного юзера»: при 2+ одновременных пользователях — тормоза и сбои. Нужно, чтобы
параллельно обрабатывалось больше клипов/загрузок и юзеры не мешали друг другу.

## 2. Диагноз — подтверждён ЖИВЫМИ данными прода (не рассуждением)

Снято `gcloud run … describe` и `gcloud logging read` 2026-07-15, проект `quip-project-500711`, `europe-west1`.

### 2.1 Что реально в бою (config)
- **`quip-api` (Service):** 2 vCPU · **8 GiB RAM** · `containerConcurrency=8` · `maxScale=10` · `timeout=900s` ·
  `REFRAME_API_CV_CONCURRENCY=1` · **тома НЕТ** (`/root/data` = tmpfs = RAM). Образ `sha256:fe3d52ee`.
- **`quip-pipeline` (Job):** 8 vCPU · 32 GiB · **реальный диск 16Gi** (`emptyDir medium=Disk`) · `timeout=8h` ·
  `RENDER_FANOUT_MAX=12`.
- **`quip-render` (Job):** 8 vCPU · 32 GiB · диск 16Gi · `timeout=20m`.

**Ключевой факт:** фикс OOM-инцидента 14 июля (том 32Gi на `quip-api`) **в проде НЕ живёт** — `deploy_prod.ps1`
пушит только `--image`, ресурсные флаги ставились руками и отвалились при последнем редеплое. Скрипт
`deploy.ps1` том прописывает — но «что в скрипте» ≠ «что в бою». Рендер-ферма (Job'ы) — здорова; проблема в
интерактивном тире.

### 2.2 Что реально в бою (боевые логи 11–14 июля)
- **OOM ×15:** `Memory limit of 8192 MiB exceeded with ~8230 MiB used` — тяжёлые эндпоинты качают `source.mp4`
  (0.7–2.9 ГБ) в 8-гиговую RAM и там же гоняют CV; совпали два → контейнер убит **со всеми чужими запросами**.
- **503-штормы:** десятки на `/reframe`, `/export/captioned.mp4`, `/edit/set-interval`, `/ass`, `/analysis`.
  Кластеры «несколько клипов одного джоба в ОДНУ секунду» → это **один юзер**: фронт выпускает 3–4
  параллельных тяжёлых запроса на открытие клипа (`prefetchNeighbors` без дедупа), они врезаются в
  **единственный** CV-слот (`=1`) → все кроме одного получают 503.
- **500/504 побочно:** `/usage`, статус джобы, `/edit` падают заодно при захлёбывании контейнера.

### 2.3 Вывод
«Еле держит одного» — буквально правда. Причина **не в объёме железа**, а в том, что тяжёлую работу
рендер-фермы делает лёгкий веб-контейнер с **1 CV-слотом и без диска**, где падение общее. «Апгрейд квоты
диска» со старой инженерной схемы — мимо: квота Job'ов здорова (single-job уже идёт 12-wide), а RAM
веб-сервиса пуста без тома. Теория «100GiB÷32 = 3 контейнера» была опровергнута ещё 2026-07-10.

### 2.4 Измерено на облаке 2026-07-15 (квоты `europe-west1` + фактическая параллельность)
- **Параллельность рендера ФАКТ = 12 контейнеров** (скан 120 последних `quip-render` executions по окнам
  start→completion; один fan-out поднимал 10 разом). Всё при квоте диска 100 GiB и без единого отказа →
  подтверждает: `sizeLimit` — потолок, не резерв; диск НЕ бьёт.
- **Живые квоты (`europe-west1`):** CPU **200 000 vCPU** · память **2 TiB** (грант выдан) · инстансы
  **безлимит** · RunningExecutions **1000** · per-instance disk **32 GiB** · **Total Ephemeral Disk 100 GiB**
  · **Job run requests 60/мин**. Пик дизайна (~16 рендеров + ~10 координаторов + веб) ≈ **288 vCPU / 1.15 TiB
  / ~26 executions** — с огромным запасом по всем, КРОМЕ двух.
- **Запросить ровно 2 (бесплатно, это потолки, платишь за факт):**
  1. **`Job run requests` 60 → 300/мин** — реально троттлит старты многих юзеров (~13 RunJob на видео ×
     5–10 юзеров > 60 → retry-backoff). Это то, что реально мешает многопользовательности.
  2. **`Total Ephemeral Disk allocation` 100 GiB → 2 TiB** — страховка под добавляемый api-диск + рост
     (20× прыжок → ручное ревью Google ~2 дня, подавать раньше).
  Остальное (CPU / память / инстансы / per-instance disk) — трогать НЕ надо.
- **Вывод «не сломается ли»:** железо и квоты держат 5–10 юзеров с запасом. Худшее БЕЗ апгрейда — старты джобов
  уходят в retry-backoff (медленнее на старте), НЕ падают. Глобальный бюджет (Фаза 1c) ещё и ограничивает
  число рендеров сверху → может только снизить нагрузку. **Квоты НЕ влияют на редактор/скачивание** (те живут
  в веб-сервисе, не в Job'ах).

## 3. Цели / Не-цели

**Цели:**
- Убрать OOM веб-тира и 503-штормы (в т.ч. для одного юзера).
- Гарантия «один юзер не может занять ресурсы другого» (изоляция интерактива от тяжёлой работы).
- Справедливость рендер-пула: большой аплоад не забивает всё, мелкий не голодает.
- Держать 5–10 одновременных пользователей/загрузок без деградации. Подтвердить **нагрузочным тестом**.

**Не-цели (YAGNI для 5–10 юзеров):**
- Не разделяем сервис на отдельный interactive/heavy тир (это подход C, под 100+).
- Не строим полноценную очередь с приоритетами/вытеснением.
- Не трогаем reframe-грид/рендер-инвариант (`REFRAME_FPS_GRID_INVARIANT`) — тяжёлую CV-логику не меняем,
  только ПЕРЕНОСИМ её исполнение с HTTP-пути в Job.
- Не трогаем репозиторий лендинга `Shorts-Automatizator`.

> попадает на НЕзапечённый клип** и валится в синхронный on-the-fly рендер под 1 CV-слот. Удаление пауз — НЕ при чём.
>

>
> ✅ **РАЗРЕШЕНО (recency-SQL, 2026-07-15): ЛЕГАСИ + ИНЦИДЕНТ, forward ЗДОРОВ.** Пре-бейк captioned

> джобы ДО 2026-07-10, (б) инцидент-джоба `bc7c4a53e6de`, чей пре-бейк-рендер OOM-убит на лету (SIGKILL → не
> `failed`, застрял `null`). **Вывод: forward-фикс пайплайна НЕ нужен** — нужны Фаза 1b (сеть) + Фаза 0

- **Механика провала:** для `NULL`-клипов (легаси/инцидент — см. баннер) условие 302 ложно → скачивание

1. **Немедленно — Фаза 0** (CV-слот 1→2, диск, 4vCPU): on-the-fly путь перестаёт ронять OOM-500 и удваивает

3. **Разовый бэкфилл легаси (batch Job):** ре-бейк ~254 клипов с `render_status=NULL` (джобы до 2026-07-10 +

4. **Пайплайн — НИЧЕГО.** Пре-бейк новых джоб уже работает (recency-SQL подтвердил forward-здоровье).
   `should_serve_cached_captioned` менять НЕ надо. **Размер всей 1b′: SMALL** (сеть 1b + бэкфилл-скрипт).

**Побочный флажок (НЕ про скачивание, отдельно):** свежие джобы `57d1dd7182cb`/`8a9c4f0c0ae5` (07-15) и
`0c558944f954` (07-14) имеют `clips=0`. Первые две — возможно, в обработке/тест; `0c558944f954` висит сутки с 0

### Фаза 1c — Справедливость рендер-пула (РЕШЕНО: глобальный бюджет in-flight)

## 5. Тестирование и верификация (жёсткие правила репо)
- **TDD на чистой логике:** математика глобального бюджета/окна fanout, атомарность счётчика (гонки
  инкремент/декремент), маппинг тикетов. Сначала падающий тест.
- **Никаких тихих фолбэков:** промах кэша/тикета → честный статус/ошибка, не выдуманное значение.
- **Идемпотентность денег:** любой новый условный PATCH к PostgREST, читающий колонку, которую сам пишет →
  `idempotent=False` (см. `test_retry_cas_safety.py`). Глобальный счётчик — CAS-осторожно.
- **Враждебный ревью диффа ДО прода** (сломать, а не «проверить») + инвентаризация ресурсов с замерами.
